# ステップ 8 · 発表者モード（任意）

語り手のために 2 つ目のウィンドウを開く：上部の固定バナーに**タイマー**とページ送りボタン、左側は
**表示中のページ**と**次のページ**のスケールされたピクセル精度プレビュー、右側は**このページで話す
プロンプト**と**全スライド総覧**。聴衆の画面には一切触れない。これは
**任意機能**であり——本番の舞台で本当に発表するとき、十数ページ以上を連続して話すとき、
あるいはユーザーが
発表者モード / presenter / プロンプト / teleprompter / 2 画面 /「ノートが表示されない」と言ったときに提供する。ファイルとして
配るだけ、PDF に印刷するだけのデッキには付けず、なぜ付けないのかを述べる。

ワークフロー上では検証と納品（ステップ 6）の後に置く：まずデッキが単独で
成立するようにしてから、ツールウィンドウを足す。

## 1. インストール

機能全体が 1 つの自己完結したブロックである：`assets/presenter-overlay.html`。

```bash
node assets/assemble.cjs deck.src.html deck.html --presenter assets/presenter-overlay.html

# ステップ 7 の筆跡レイヤーと併用する（順序は固定：ink が先、presenter が最後）
node assets/assemble.cjs deck.src.html deck.html \
  --ink assets/ink-overlay.html --presenter assets/presenter-overlay.html
```

デッキの DOM、CSS、`deck-shell.js` を書き換えることはない。アセンブラはこれを丸ごと
`</body>` の直前へ連結し、両方が要求されたときは ink ブロックが先に来る。納品前に、
ファイル内で印を付けた 2 つの設定ブロック**だけ**を編集する。

シェルの 2 つの部分に依存する：`#stage > .slide` 構造と `window.__deck`。
`__deck` が無いときオーバーレイは有効にならず、コンソールに `noShell` の 1 行を書く——
デッキはそのまま再生される；これを足しても壊れたボタンが残ることはない。

## 2. 各ウィンドウが担うもの

**聴衆ウィンドウ**（通常のデッキ）——変わるのは以下だけである：

| キー | 作用 |
|---|---|
| `S` | 発表者ウィンドウを開く / 更新する |
| `N` | ページ下部に**プロンプトバー**を出す（ポップアップがブロックされたときのフォールバック；同じプロンプト文） |
| `Esc` | プロンプトバーを閉じる |

**発表者ウィンドウ**——上部に固定のバナー（経過時間、`現在 / 総ページ数`、前へ / 次へ / リセット；
カードではなく、ドラッグもサイズ変更もされず、位置の記憶もされない）に加えて 4 枚の吸着カード。ヘッダーを
ドラッグして移動し、右下の角をドラッグしてサイズを変える；位置はデッキの URL ごとに記憶される。

| カード | 内容 |
|---|---|
| 現在のページ | 表示中のスライド、スケール済み、ちらつきなし |
| 次のページ | 次のスライド；最終ページでは「— デッキの最後 —」と表示される |
| プロンプト | 骨子 §7 にあるこのページのプロンプト（§6 を参照） |
| 総覧 | すべてのスライドを `?preview=N` サムネイルの横並びフィルムストリップに；ホイールでスクロールし、クリックで両ウィンドウがジャンプ；ストリップのビューポート付近の約 8 個だけ実際に iframe がマウントされる |

| キー | 作用 |
|---|---|
| `← →` `↑ ↓` `Space` `PageUp/Down` | ページ送り、**そして聴衆ウィンドウも動かす** |
| `Home` `End` | 最初 / 最後のページ |
| ホイール（総覧の上） | フィルムストリップをスクロール；サムネイルのクリックで両ウィンドウがジャンプ |
| `R` | タイマーをリセット |
| `Esc` | ウィンドウを閉じる |
| ヒントバーの「レイアウトをリセット」 | 記憶した位置を忘れ、既定の 4 枚のカードに戻す |

同期は**双方向**である：聴衆ウィンドウでページを送るとプレビューが追随し、発表者ウィンドウで
ページを送ると聴衆ウィンドウも追随する。

## 3. プレビューはこのデッキそのもので、スクリーンショットではない

カードに映るのは、同じ HTML ファイルを `?preview=N` 付きで開き直したものである。シェルはこのパラメータを
認識して、次のことを行う：

- `<html data-preview="1">` を付け、ページ N へ直接着地する；
- 総覧を構築**せず**、`location.hash` も書か**ず**、キーボード・クリック・タッチのページ送りを
  無効にする——プレビュー内の誤ったクリックが本番のデッキを引きずることは決してない；
- すべての `go()` で `deck:go` CustomEvent を発行し、発表者オーバーレイはこれを監視して
  ページ番号をブロードキャストする。

ウィンドウ間でやり取りされるのは数字だけであり、iframe が再読み込みされることはない（`preview-ready` ハンドシェイクが
1 度だけ位置を補正し、それによってプレビューのちらつきが防がれる）：

| メッセージ | 方向 | 目的 |
|---|---|---|
| `deck-goto {idx}` | 聴衆 → 発表者 | プレビューが追随 |
| `presenter-goto {idx}` | 発表者 → 聴衆 | 逆方向のページ送り |
| `presenter-open` | 発表者 → 聴衆 | ハンドシェイク：現在のページを送り、ウィンドウを開いてもスライド 1 に着地しないようにする |
| `preview-goto {idx}` | 発表者 → カード内 iframe | 再読み込みせずにページを変える |
| `preview-ready` | カード内 iframe → 発表者 | 上記の位置補正の引き金 |
| `ink-cmd {cmd, arg/store…}` | 発表者 ↔ カード内 iframe | 注記の遠隔操作と筆跡ペイロード（§3.5） |
| `ink-state {on}` | カード内 iframe → 発表者 | プレビューの筆跡レイヤーが切り替わり、チップが追随する（現在のページの iframe からのみ受け付ける） |
| `ink-store {store,rev}` | 発表者 ↔ ホスト | ストア全体の筆跡中継、リビジョンで保護（§3.5） |

発表者ウィンドウは `window.opener` を通じてホストを見つけ、opener が無いときは `window.parent` に
フォールバックする（`parent === window` のときは除く）。したがって同じファイルがポップアップでも
埋め込みでも動作し、同期が黙って壊れることはない。

## 3.5 注記の中継（ステップ 7 も導入されている場合のみ）

発表者ウィンドウには**直接注記できる**：プレビューの iframe はすでにこのデッキそのものなので、
その中の筆跡レイヤーは同じエンジンである——何もコピーされず、2 つ目のストアも存在しない。
発表者オーバーレイが行うことは：

- `pointer-events` を**現在のページのカードだけ**で復活させる
  （`#c-cur .pbody iframe{pointer-events:auto}`）；次のページのカードは `pointer-events:none` のまま；
- 現在のカードのヘッダーに「注記」チップを追加し（`COPY.inkBtn / inkBtnOn`）、それが
  `ink-cmd{cmd:'on'}` を iframe へ送る；プレビューの筆跡レイヤーは `ink-state` で応答し、
  チップが追随する。プレビュー内の小さなタイルボタンをクリックしても動作する——両方の経路は収束する；
- 筆跡は筆跡レイヤーのリビジョン・プロトコルで中継する（ステップ 7 §5）：保存した側がブロードキャストし、
  相手はより新しいリビジョンだけを採用し、エコーは吸収され、**最後の書き込みが勝つ**。筆跡と取り消しは
  両方のウィンドウで一致し続け、取り消しはウィンドウをまたぐ（遠隔の乗っ取りは 1 つの `k:'*'` ステップである）；
- 各筆跡の後、iframe はキーボードを返却する（`parent.focus()`）ので、← → で即座にページ送りできる。

**既知の制限**（納品メモに記すこと）：プレビューの iframe は決して再読み込みされないので、同期はリフレッシュではなく
メッセージを介して行われる；両側が同じ `localStorage` キーに書き込み、2 つのウィンドウが
本当に同じ瞬間に描いた場合はリビジョンが決める——最後に描かれた筆跡が勝つ。これは
設計であって、バグではない。

## 4. 設定ブロック 1 · COPY——このデッキ向けに文言を書き直す

ファイル先頭にある最初の編集可能な領域で、言語ごとに 1 つのオブジェクト；言語は
`<html lang>` から選ばれる。次の 3 つは**必ず**見直す：

- `cardPrompt`（既定 "Prompt" / 提示词）——このラベルはトーク中ずっと画面に出る；話し手自身の
  言葉にする；
- `empty`（"(no prompt for this slide yet — see skeleton §7)"）——プロンプトが欠けているとき、この
  行はウィンドウで最も目に付くものになる；プレースホルダーの匂いを残したまま納品しない；
- `hintDrag`——話し手にカードを動かさせたくない場合は、この行を削除して既定のレイアウトのままにする。

`blocked` はポップアップがブロックされたときの通知であり、フォールバック手順も兼ねる；翻訳するときは
2 つの節（まず何をするか、次に代替手段）を残す。

## 5. 設定ブロック 2 · CANVAS + TOKEN_MAP——形状と配色はこのデッキから取る

- `CANVAS` はこのデッキの論理キャンバスと一致しなければならない（シェルの既定は 1280×720）。プレビューカードは
  厳密に `min(cardWidth/CANVAS.w, cardHeight/CANVAS.h)` でスケールするので、値が違えば
  サイズも違う；キャンバスが 1280×720 でないデッキはここを変更しなければならない。
- `TOKEN_MAP` は 7 つのカスタムプロパティを読む：`--bg --panel --ink --muted --accent --warn --rule`。
  このうち `--panel/--muted/--warn/--rule` は**スターターテンプレートに存在しない**；欠けているときは
  組み込みのレシピにフォールバックし、`tokenMiss` をコンソールに書く。クライアントの実際の
  パレットを発表者ウィンドウへ持ち込むには、骨子のステップ 2 の `:root` ブロックでこの 4 つを宣言する。

配色は同じ `:root` を読むことで継承されるので、発表者ウィンドウが所属するデッキから決して
乖離しない；明色か暗色かは `--bg` の相対輝度
（閾値 0.22）から選ばれる。

**下限は依然として推測ではなく実測である。** オーバーレイには 4.5:1 のガードが組み込まれている：
`--ink/--muted/--accent/--warn` が**カードの下地**（`--panel`、または
明暗の既定）に対して 4.5:1 を下回って測定されたとき、その 1 色だけが既定に戻り、
`--accent #F0D9E4→#1F4FD8` のようなエントリがコンソールに書かれる。プロンプト本文は 19px、カードタイトルは
11px——小さな文字なので 4.5:1 は厳しい線である；淡いピンクのアクセントは、
舞台で見えない強調を生むのではなく、既定の青へ戻らなければならない。

2 つの実在のレシピで実測した比（前景色 / カードの下地 → 比）：

| ケース | ink | accent | warn | muted |
|---|---|---|---|---|
| 明色のデッキ（`#FFFFFF` カード） | 19.44 | 6.22 | 5.93 | 6.40 |
| 暗色のデッキ（`#181C21` カード） | 14.20 | 9.57 | 7.44 | 6.50 |

意図的に壊したデッキ（白いカード上で `--accent:#F0D9E4`、`--warn:#FFF2C8`、`--muted:#EDEDEB`）を使い、
ガードを確認した：3 つとも捕捉され、`#1F4FD8 / #8A5A00 /
#5C5F66` に置き換えられた、フォールバック後の最悪の比は 5.93 である。ガードは**ウィンドウを開いたときに 1 回だけ**実行されるので、
出荷時の悪いパレットは防ぐが、セッション途中の色変更は防がない——色を変えたら
ウィンドウを開き直すこと。

## 6. プロンプトカードに入れるもの

情報源は 1 つだけ：骨子 §7（`04-skeleton.md` を参照）。そのページのプロンプトをそのページの
`<aside class="notes">…</aside>` の中へ逐字そのまま入れて実現する。カードが消費するのはそれだけで、`data-count` も
`hint` も取らず、notes の HTML だけを取る——したがって §7 のマークアップがそのまま描画される：

| タグ | 描画 | 用途 |
|---|---|---|
| `<strong>` | 警告色 | 声に出して言わなければならないキーワードや数字 |
| `<em>` | アクセント色 | 問いかけ、間、動作 |
| `<code>` | 等幅のチップ | 用語、フィールド名、コマンド |

骨子 §7 の 3 つの規則は依然として有効である：逐字原稿ではなく合図、150–300 文字、話し言葉の文体。数字は
ステップ 6 の数字監査に縛られたままである——そのスライドのどの §4 エントリも担っていない数字が
（それが `data`、`table`、`formula` のどれであっても）プロンプトに現れるのは、ページ上のものと同じ違反である。notes は聴衆ウィンドウに決して描画されず、印刷もされない；
その違いを納品メモで明らかにする。

## 7. 検証：これらのアサーションは実際に実行されなければならない

同梱のブラウザはしばしばポップアップをブロックする（`window.open` が null を返す）。これは機能の
欠陥では**ない**：まず実際のキーイベント（`press_key`）で 1 回試し、ブロックされたら `blocked` 分岐と
フォールバックを検証する。自動化の下で同期をテストするには、`window.open` を、捕捉した HTML を載せた
iframe へ `postMessage` を転送するスタブに置き換える——そうすれば両方のメッセージ経路が
同じ実コードを実行する。

```js
async () => {
  const sleep = ms => new Promise(r => setTimeout(r, ms));
  const key = k => document.dispatchEvent(new KeyboardEvent('keydown', {key:k, bubbles:true, cancelable:true}));
  const out = {};
  // 1) フォールバックのプロンプトバー：開き、クリックしてもページ送りせず、ナビゲーションに追随し、Esc で閉じる
  key('n'); await sleep(250);
  const dr = document.getElementById('pv-drawer');
  out.drawer = {open: dr.classList.contains('open'), idx: dr.querySelector('.pv-idx').textContent};
  const before = window.__deck.index;
  dr.dispatchEvent(new MouseEvent('click', {bubbles:true, cancelable:true}));
  await sleep(350);
  out.clickDoesNotPage = window.__deck.index === before;
  key('Escape'); await sleep(200); out.escCloses = !dr.classList.contains('open');
  // 2) シェルのリグレッション：総覧、数字ジャンプ、ハッシュがすべてまだ動く
  key('g'); await sleep(300);
  out.overview = document.getElementById('overview').querySelectorAll('.thumb').length;
  key('g'); await sleep(250);
  key('3'); await sleep(450); out.digit3 = {idx: window.__deck.index, hash: location.hash};
  // 3) 発表者ドキュメントの中身：捕捉した HTML を srcdoc iframe に渡し、約 2.5 秒待ってから読む
  const f = document.getElementById('pvtest'), d = f.contentDocument, w = f.contentWindow;
  out.errs = w.__errs;                                     // 空でなければならない
  out.cards = [...d.querySelectorAll('.pcard')].map(c => c.id + ' ' + c.style.left + ' ' + c.style.top);
  out.iframeSrcs = [...d.querySelectorAll('iframe')].map(i => (i.getAttribute('src')||'').split('?')[1]);
  out.prompt = d.getElementById('pmt-body').innerHTML;      // §7 の strong/em/code が残っていること
  out.nxtAtEnd = d.getElementById('m-nxt').textContent;      // 最終ページは END と表示されること
  // 4) 双方向同期：聴衆のページ送り → カードが追随；発表者のボタン → 聴衆が追随
  key('ArrowRight'); await sleep(700); out.hostToCard = window.__deck.index + ' / ' + d.getElementById('t-count').textContent;
  d.getElementById('b-prev').click(); await sleep(700); out.cardToHost = window.__deck.index;
  // 5) レイアウト：カードをドラッグ → localStorage に pv.v2|<deckUrl> が入る → 閉じて開き直すと位置が残る
  out.lsKey = Object.keys(w.localStorage).find(k => k.indexOf('pv.v2|') === 0);
  // 6) 総覧：バナーは固定、フィルムストリップは仮想化、クリックで両ウィンドウがジャンプ
  out.bannerH = d.getElementById('banner').offsetHeight;           // 52；#banner は .pcard ではない
  const strip = d.getElementById('ovw-strip');
  strip.dispatchEvent(new WheelEvent('wheel', {deltaY: 1200, bubbles: true, cancelable: true}));
  await sleep(300); out.ovw = {moved: strip.scrollLeft > 0, mounted: strip.querySelectorAll('iframe').length}; // マウントは 8 以下
  d.querySelector('.ovw-item[data-i="5"]').click(); await sleep(700); out.thumbJump = window.__deck.index; // 5 でなければならない
  return JSON.stringify(out);
}
```

さらに 3 つを個別に確認する：

- **プレビューページは単独で成立する**：`deck.html?preview=2` を直接読み込む——スライド 2 に着地し、
  `data-preview="1"` を設定し、キーボードとマウスのページ送りをすべて無視し、`#overview` を空のままにし、
  ハッシュを書かないこと。
- **外部リクエストはゼロ**：オーバーレイも、生成された発表者ドキュメントも、
  `//` で始まるリソースを参照してはならない；`list_network_requests` に現れるのはこの 1 つの HTML ファイルと
  それ自身の `?preview=N` iframe の読み込みだけであるべきである。
- **コントラスト比**：§5 の表に照らしてこのデッキの実際の配色を測り直す。特にデッキが
  `--accent` を上書きしている場合はそうする。ガードが色を差し替えたなら、納品メモでそれを名指しし、
  デッキの配色を直すか既定を受け入れるかをユーザーに決めさせる。

## 8. 既知のトラップ

- **`file://` のオリジン。** 発表者ドキュメントは `about:blank` のポップアップへ
  `document.write` で書き込まれるので、デッキのオリジンを継承する。`window.open('presenter.html')` や
  絶対 URL に切り替えると `file://` ではクロスオリジンになり、`postMessage` も `localStorage` も
  壊れる。**これを「整理」して絶対 URL にしないこと。**
- **`BroadcastChannel` を使わない。** `file://` のページは不透明なオリジンとして扱われることが多く、このチャネルは
  間欠的にしか動かない。ここではすべてが明示的な `postMessage` であり、ポップアップと
  埋め込みの両方をカバーする（§3 の opener/parent フォールバック）。
- **`localStorage` が持つのはカードのレイアウトだけ**であり、キーは `pv.v2|<パラメータなしのデッキ URL>`。これは
  skill 全体で唯一ストレージに触れる箇所である——それを明示すること。別のマシンや
  ディレクトリへ移すとレイアウトは既定に戻る；プロンプトの言葉は 1 語も失われない、それらは HTML にあるのだから。
- **レイアウトキーには版がある。** `pv.v1` → `pv.v2` はカード集合の変化（タイマーカードが外れ、
  総覧カードが入った）で生じたもの：古い保存レイアウトは 1 回無視されてウィンドウは既定の
  形状に戻る；取り残された古いキーは二度と読まれず、そのまま残してよい。
- **総覧は仮想化されている。**サムネイルの iframe は同時に最大約 8 個だけマウントされる——ストリップの
  ビューポート付近だけ——で、残りはページ番号 + タイトルのプレースホルダー；サムネイルの筆跡は
  マウント時の `localStorage` を映すだけで、長いデッキでウィンドウを開くと最大 8 回の
  同じファイルの `?preview=N` 読み込みが追加で走る。
- **ポップアップのブロックは異常ではない。** ブラウザが遮り、プロジェクションソフトが遮り、
  一部の企業向けビルドは常に遮る。したがって `N` のプロンプトバーは飾りではなく、遮られた後に語り手が
  プロンプトを見る唯一の道である；`blocked` の文言は両方の経路を述べなければならない。
- **発表者側の UI のクリックでページを送ってはならない。** シェルは左右の半分へのクリックを「ページを
  めくる」こととして読む。発表者側のすべてのクリック可能な要素（プロンプトバー、通知）は `stopPropagation` を呼ぶ；
  新しいコントロールにも同じことをする。さもないと語り手がプロンプトに手を伸ばしたときにデッキが飛ぶ。
- **`CANVAS` が骨子と一致しない**と、プレビューのスケールが狂い「ぼやけて」見える。
  両方の箇所を同時に変更すること。
- **ページ送りは iframe を再読み込みしない。** したがって登場アニメーションと `data-count` のカウントアップは
  初回読み込み時に 1 度だけ走る。ページごとに再生される動きに依存するデッキでは、それを既知の
  制限として納品メモに記録する；再読み込みの遅延を足してはならない——それはちらつきを代償にアニメーションを得ることになる。
- **両方のオーバーレイを導入した場合**、`Esc` は筆跡レイヤーのバブルメニューとプロンプトバーを
  干渉し合わずに個別に閉じる；`S`/`N` は発表者側だけのものである。筆跡レイヤーが使うのは `Z`/`Y`。

## 9. 納品メモに必ず加えること

ステップ 6 の報告の上に：

- 発表者モードの開き方（ウィンドウは `S`、プロンプトバーは `N`）と、**今回ポップアップの
  経路を本当に検証したか**——自動化環境が遮った場合は、「ポップアップの
  経路はブロック分岐を通して検証し、2 ウィンドウ同期は等価な `postMessage`
  転送で検証した」と述べ、「テスト済み」と曖昧にぼかさない；
- プロンプトは骨子 §7 に由来し、ユーザーのレビューを受けていること、あるいは「発表者モードは未導入」であること；
- 発表者レイヤー自身の `localStorage` の用途はカードのレイアウトだけであること（`pv.v2|`）；ステップ 7 を
  導入している場合、プレビュー内の筆跡レイヤーは自分自身の `ink.v1*` キーを書く（筆跡レイヤーが
  所有する）；両側で同じキー、同じオリジン、リビジョンによって同期する；
- ステップ 7 を導入している場合：発表者ウィンドウは直接筆跡を受け取り、ウィンドウをまたぐ筆跡は
  「最後の書き込みが勝ち」、プレビューは決して再読み込みされず、同期はリフレッシュではなくメッセージで伝わる；
- プロンプトは印刷されず PDF にも届かないこと、そして `notes` が聴衆ウィンドウで決して見えないこと。
