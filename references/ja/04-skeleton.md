# ステップ 4 · Agent-native 骨子（構築仕様書）

出力：`<トピック>-HTML-PPT骨子.md`（中国語版の慣例：`<主题>-HTML-PPT骨架.md`）。これは**agent 向けの構築仕様書であり、台本ではない**：ステップ 5 がこれを 1 行ずつ実行し、ユーザーが 1 行ずつ審査して直す。書き終えたら必ず止まり、レビューを待つ。

## ファイルの形

```markdown
# HTML PPT 骨子 · <トピック>（<語りの仕掛け>）

> 本ファイルは agent 向けの**構築仕様書**であり、スピーカーノートではない。§1 と §4 に厳密に従って単一ファイルの HTML デッキを生成すること。
> データは `<トピック>-資料まとめ.md` からのみ取ってよい。**そのファイルに無い数字は決して捏造してはならない**；あるスライドに新しいデータが要るなら、先に調べて出典を付け、それから埋める。

## §1 構築仕様（YAML）
## §2 語りの仕掛け            ← 問いの連鎖 / 語り手 / 全体ルール
## §3 幕構成                  ← 表 + レンダリングされるページ順 + 中心の問い
## §4 スライド別仕様           ← キーワード集合を宣言し、各スライドをキーワードで記述する
## §5 実装メモ                ← agent のチェックリスト + セルフチェック項目
## §6 変更履歴                ← 改訂ごとに追記；現状が優先
## §7 スピーカープロンプト（任意） ← ステップ 8 を実行するときだけ；最後のセクション、ページごとにレビュー
```

## §1 構築仕様（YAML・フィールドごと）

```yaml
deck:
  format: single-file HTML          # 1 つの .html、<style> と <script> はインライン、何も外に出さない
  filename: <トピック>.html
  canvas: 16:9                      # 1280×720 の論理サイズ、CSS transform でウィンドウに合わせて拡大縮小
  slides: <N>                       # §3 のレンダリング順のエントリ数と一致しなければならない
  language: <zh-CN | en>
  team_on_cover: <名前>             # 任意；そのページがあるなら分担も書く
  navigation:                       # ハード要件、05-build.md を参照
    - Space / → / ↓ / PageDown → 次へ；← / ↑ / PageUp → 前へ；Home / End → 最初/最後
    - G → グリッド総覧（サムネイルの壁）；F → 全画面；数字キー 1-9 → ジャンプ；Esc → 総覧を閉じる
    - 画面の左半分 / 右半分をクリックしてページ送り；タッチでスワイプ
    - モバイル縦向き → 「横向きにしてください」のマスクを表示
  typography:
    cn: <フォントスタック>          # ステップ 2 より
    numbers: tabular-nums、主役の数字 72–120px
    min_body_px: 22
  theme:
    light: {bg:"", panel:"", ink:"", muted:"", accent:"", warn:"", rule:""}
    dark: {…}                       # デッキにはどちらか一方だけを選ぶ
    constraints: [<グラデーションの塗り、グラスモーフィズム、影の重ね、…>]
  charts: インライン SVG または純粋な CSS；外部依存なし；ネットワークリクエストなし、localStorage なし
  presenter: off | on（on = ステップ 8 を実行；プロンプトは §7 にある；on のとき、localStorage は発表者ウィンドウだけが使う）
  footnotes: すべてのスライドの右下に出典バー、「出典 · 年」、9–11px
  accessibility: スライドごとに h1/h2 の順序を守る；ページ変更時に aria-live で読み上げ；本文のコントラスト ≥ 4.5:1
  motion: <切り替えの種類、時間、イージング；ページ内アニメーションの種類>；prefers-reduced-motion では無効
```

`typography` / `theme` / `constraints` / `motion` はステップ 2 のスタイル決定ブロックからそのまま写す——ここで作り直してはならない。切り替えの種類・時間・イージング・ページ内アニメーションの種類は明示的に書き、構築はそれに従う。暗色のデッキでは、`deck-shell.css` の `--ovl-bg / --ovl-ink / --ovl-card`（総覧の壁）も同じ系統に上書きされていることを確認する。

## §2 語りの仕掛け

3 つを書く：主要な方法（例：問題提起 → 問い → 分析 → 結論）、推進エンジン（問いの連鎖。すべてのスライドが少なくとも 1 リンクは進める）、そして語り手と全体ルール（コードネーム、役割、立場を一言、そして「どの数字も、誰が測り、いつの年で、境界がどこまでかまで必ず言う」といったルール）。

## §3 幕構成

| 幕 | スライド | 機能 | 時間 |
|---|---|---|---|

表の下に、**レンダリングされるページ順**を 1 行で書く。例：
`1 cover / 2 act-divider / 3 kpi-hero / … / N references`——型名の後ろに普通の言葉を添えるのは構わない（`3 kpi-hero 冷たいオープニング`）が、**その前にあるのは §4 のページ型ライブラリに存在する `type` でなければならない**；「フック」「つかみ」といった裸のラベルは認めない。続けて「フッターの `NN / N` と `data-i` は構築順で振り直される——手で書かないこと」と注記する。最後に**中心の問い**（デッキ全体で 1 つ）を単独行で書く。

## §4 スライド別仕様 · まずキーワードを選び、それからスライドを埋める

スライドの書き方は 1 通りではない：データ対比のスライドは「数字 + グラフ」で走り、教材のスライドは「用語 + 例題 + 授業内クイズ」で走り、コードのスライドは「抜粋 + 行ごとのウォークスルー」で走り、審査のスライドは「方法 + エビデンス + 限界」で走る。だから §4 は万能のテンプレートではない——**キーワードライブラリ**である。内核の 3 語はどのスライドにも必須で、残りはライブラリからスライドごとに 5–8 語選ぶ。**書いた語の順序が、そのスライドの上から下への構築順になる。**

### 内核の 3 語（すべてのスライドで必須）

| キーワード | 意味 | 制約 |
|---|---|---|
| `type` | ページ型名。下のページ型ライブラリを参照 | 1 つのデッキで 6–8 種に抑える。そうしないとスライドごとにレイアウトを描き直すことになる |
| `key` | そのスライドの唯一の主張 | ≤ 8 語 / ≤ 22 字、1 スライドに 1 つ；`.key` として描画される |
| `sec` | そのスライドの所要時間 | デッキ全体の `sec` の合計 ≈ ステップ 1 の予算；超過したらスライドを削る前にキーワードを削る |

### まずこのデッキのキーワード集合を宣言する

§4 のスライド記述の 1 行上に、このデッキが使うキーワードを列挙する（内核の 3 語を含め、合計 12–24 語；1 つのスライドが実際に使うのはそのうち 5–11 語だけ——この行はデッキ全体の和集合であり、スライド数とともに増える）：

```
keywords: type key sec topic title points data table compare bars emphasis ask hint
```

- **この行に無いキーワードは、§4 のどのスライドにも現れてはならない。** 構築 agent が向き合うのは常に 1 つの統制語彙であり、スライドごとの即興ではない。
- 途中で 1 語足す場合：まずこの行を延ばし、次に §6 に「新しいキーワード `xxx`（s12 が必要）」という行を記録する。
- 足す前のセルフチェック：既存のキーワードがすでにそれを表しているならそちらが勝つ（「まとめ」は `takeaway` であり、新しい `summary` ではない）。デッキが確定したら、使わなかったキーワードをこの行から削除する。
- **予算に合わせて削るのは、このデッキが本当に一度も使わない語だけに限る。** 下のハード制約が名指しする語は削除の対象外：あるスライドが強い色を使うなら `emphasis` が要り、数字が 2 つ以上のキーワードにまたがるなら `data` が要る。それらがこの行にあるかどうかはスライドが決めるのであって、予算が決めるのではない。

### レビュー用の凡例（`keywords:` 行のすぐ下 · 人間が読み、agent は飛ばす）

骨子は、この文書を一度も読んだことのない人がレビューする。だから `keywords:` 行のすぐ下に、**このデッキが実際に宣言した**キーワードを 1 語 1 文の平易な言葉で説明する引用ブロックを足す。**⧉ の 2 行のマーカーは必須で、そのまま写すこと**；間は §4 の系統を A→F の順にたどり、宣言済みの語だけを並べる。次の形で書く（3 系統だけ示す——残りも同じ要領で埋める）：

```markdown
> ⧉ 語句凡例 開始 · 人間のレビュー専用。ステップ 5/6/7/8 は決してここを読まない
> **このデッキが使うキーワード**（PPT には決して現れない）
> すべてのスライド：`type` ページ型 · `key` そのスライドが言う唯一の一文 · `sec` どれくらいの長さか
> A 位置づけ：`topic` どのセクションか（画面上の眉標）· `toc` アジェンダの項目
> C データ：`table` 表 · `kpi` 主役の数字 · `data` 数字の索引（画面に出さず、監査用）
> F 伝達：`hint` あなただけが見えるメモ · `ask` 投げかける問い · `discuss` オープンな議論
> スライド上のキーワードの順序 = 画面上の上から下への順序。この表に無い語を見つけたら線を引いてください——私の宣言が遅れていた語です。
> ⧉ 語句凡例 終了
```

ルールは 4 つ：

- **宣言した語だけを説明する。** 12 語を宣言したら説明も 12 個。ライブラリ全体を骨子に貼り付けてはならない——完全な表はこの文書にあり、個々のデッキにあるのではない；2 部あれば真実も 2 つになる。
- 1 語につき 1 文、できるだけ ≤ 20 字、平易な言葉で：「スピーカーメタデータ」ではなく「あなただけが見えるメモ」と書く。`.notes` / `.key` のスロットは、レビューする人に見え方が変わる場合にだけ触れる。
- **このブロックは人間専用の素材であり、agent は復唱も突き合わせもせず、これをもとに構築しない。** ステップ 5 が骨子を読むときは `⧉ 語句凡例 開始` から `⧉ 語句凡例 終了` へ直接飛び、その間を 1 行も読まない——そこは §4 のライブラリの写しであり、読んでもコンテキストを無駄に消費するだけである。意味が要るなら、この文書に戻ってくる。このブロックは `>` の引用で、DOM を生まず、その語のどれかが完成 HTML に現れたら違反である。
- ユーザーが語集合を編集したら同期を取る；凡例と `keywords:` が食い違ったときは **`keywords:` が勝つ**——ステップ 6 はこれを追わず、ステップ 4 が凡例を直す。

### キーワードライブラリ（6 系統；`★` = よく使う）

**A 位置づけ —— このスライドは何か**

| キーワード | 何を書くか | どこに落ちるか |
|---|---|---|
| `topic` ★ | このスライドが属するセクション / テーマ名、≤ 12 字 | `.kicker` の中の `.act` テキスト |
| `act` | 幕のマーカー（「第 III 幕」） | 同じ行、`topic` の前 |
| `role` | 語りの中での機能：フック / 推進 / 橋渡し / 収束 | §3 と突き合わせるだけ、画面には決して出さない |
| `toc` | 目次またはアジェンダの項目 | アジェンダのスライド専用 |

**B テキスト —— 聴衆が読むもの**（これらを合わせたものがそのまま画面上のテキストであり、別途「画面上のフィールド」は存在しない）

| キーワード | 何を書くか | どこに落ちるか |
|---|---|---|
| `title` ★ | スライドのタイトル | `<h2>` |
| `sub` | 副題 / 限定語（「2024 年の料金で試算」） | タイトルの下の小さな行 |
| `points` ★ | 箇条書き、3–5 項目、各 ≤ 20 字、1 項目に 1 つの考え | `<ul>` |
| `prose` | 本文の段落、≤ 2；「走り読み」より「読み込み」が勝つときだけ（長い叙述、抜粋） | `<p>`、≥ `min_body_px` |
| `lead` | 導入：このスライドがなぜ存在するかを 1 文で | タイトルと本文の間 |
| `defs` | 用語定義を `用語 = 定義` の形で、2–4 個 | 定義カード |
| `quote` | 他人の言葉。必ず話者 + 出典 + 年を付ける | 引用ブロック + 出典バー |
| `pull` | 引きの一文、感情のアンカー、1 スライドに最大 1 つ | 大きな文字のブロック |
| `steps` | 番号付きの手順、3–6 個、それぞれ動詞で始める | ステップ帯 |
| `cast` | 人物表：名前 + 役割 + 立場を 1 行（事例の追体験、書籍の登場人物、チームの分担） | 人物カード |

**C データ —— 何で証明するか**（ここのキーワードはすべて下のエビデンスルールに縛られる）

| キーワード | 何を書くか | どこに落ちるか |
|---|---|---|
| `data` ★ | このスライドの数字の**索引**：`どのキーワードのどの行 → 出典 · 年`。**値を書き写してはならない**（それは 2 つ目の真実であり、選定ルール 3 に反する）；数字が 2 つ以上のキーワードにまたがるときだけ使い、1 か所に収まっているならこの行ごと落とす | 監査のアンカーで、直接には描画されない |
| `table` ★ | 表：列名 + 2–6 行、各列の口径と単位を明記 | `<table>`、`tabular-nums` |
| `kpi` ★ | 主役の数字 1–4 個：値 + 単位 + 「何を測っていて、境界がどこにあるか」を 1 行 | 72–120px + `data-count` |
| `compare` ★ | 同口径の比較、2 つの型：**定量**——両側の口径 + 差；**定性**——似て見える 2 つをどう見分けるか（`溶解 ≠ 融解`：片方には判定があり、もう片方には無い）。「数字が無い」からといって言葉が無くなるわけではない | 2 段組または対照バー |
| `bars` `line` `stack` `pie` | 棒（桁がまたがるときは対数）/ 折れ線（指数化し、起点の値を x 軸ラベルに畳む）/ 積み上げまたはウォーターフォール / 構成比 | インライン SVG、軸・単位・年を明記 |
| `rank` | 順位づけ、Top N（N ≤ 6） | ランキング帯 |
| `timeline` | 年表のノード：年 + 出来事 +（任意で数字） | 横帯 |
| `formula` | 式 + 各変数の意味 + 代入を 1 回 | 式ブロック + 変数表 |
| `code` | コード片 ≤ 12 行、言語を明記し、重要な 1–2 行を指し示す | `<pre>` + ハイライトクラス |

**D ビジュアル —— どんな見た目か**

| キーワード | 何を書くか | どこに落ちるか |
|---|---|---|
| `visual` ★ | 画面の指示：どのグラフか、軸をどうラベルするか、どのブロックが warn 色を取るか | 構築はそれに従って描く |
| `layout` ★ | 構成：段数、階層、余白がどこか（「左 40% はタイトル、右 60% はグラフ」） | `.slide-body` の形を決める |
| `media` | 写真 / スクリーンショット / イラスト / 画面録画：内容、ライセンス、見る人に必ず見えなければならないもの。デッキはオフラインの単一ファイルなので、録画は数秒の軽い GIF にする——でなければ `demo` としてライブでやる | `.img-frame` + `aspect-ratio` |
| `icon` | アイコンの意味（emoji はアイコンではない） | インライン SVG |
| `emphasis` ★ | そのスライド唯一の視覚的な焦点：accent か warn か、どの要素に置くか | 1 スライドに強い色は 1 つ |
| `before-after` | 昔と今 / パッチと修正 / 誤読と訂正 | 2 段組 |
| `diagram` | 構造図：原理、アーキテクチャ、流れ、**帰属ツリー / 5-Why / フィッシュボーン**——どのブロックがあり、どうつながり、矢印がどちらを向くか。因果連鎖のノードは名詞でよい（動詞を要求する `steps` とは違う） | インライン SVG |

**E 論証 —— どう説得するか**

| キーワード | 何を書くか | どこに落ちるか |
|---|---|---|
| `missing` | **あるべきなのに無いもの**：配線されなかった警報、一度も走らなかった検査、排除された仮説、答えられないままの問い。「何が欠けているか + それが何を犠牲にしたか」を書く——これはすべての振り返りの半分であり、教材の中核の動きでもある；`points` に押し込んではならない | 欠落カード、warn 色 |
| `evidence` | 主張を支えるもの。`data` / `table` / `quote` のどの行かを指す | 相互参照 |
| `caveat` ★ | 限界と境界条件——「ここから先では成り立たない」 | 小さな文字 + ⚠️ |
| `counter` | 最も強い反論 + このスライドがそれにどう答えるか | `evidence` の隣 |
| `analogy` | 抽象的な仕組みのための類推（類推はデータを負担しない） | 1 行 |
| `example` ★ | 具体的な事例または例題：対象 + 状況 + 結果 | 事例カード |
| `takeaway` ★ | 聴衆が持ち帰る 1 行 | 収束ブロック |
| `action` ★ | アクション項目 / 次の一手 / 改善項：誰が + 何を + いつまでに、任意で「何ができていれば完了か / 現在の状態」、2–4 行。**4 行を超える場合、または状態の列が要る場合は、そのページを `table` に譲る——`action` と `table` は同じスライドを共有しない**（同じ内容を 2 回書くことになり、選定ルール 3 に反する） | アクション一覧 |
| `transition` | 次のスライドをどう引き出すか（問いか、半端な文か） | フッターの近く |

**F 伝達 —— 誰が何を話すか**

| キーワード | 何を書くか | どこに落ちるか |
|---|---|---|
| `hint` ★ | スピーカーノート：どこを強調し、どこで人がつまずき、追加の質問にどう答えるか | `.notes` |
| `ask` | ホストまたは話者が投げかける問い | 画面に出すか、ノートにだけ書くか——どちらか一方 |
| `lines` | 語り手のセリフ（8–28 字、専門用語の解説はしない）、**複数語り手のデッキ専用** | 語り手カプセル + セリフ |
| `demo` | ライブの操作：手順 + 何が現れるはずか + 壊れたときの代替 | デモ用のスライド |
| `quiz` | 授業内の問い：問題文 + 答え + 何を試すか | 答えは `hint` に書き、スライドには決して出さない |
| `task` | 実技課題 / 宿題：要件 + 提出物 + 締切 | 課題カード |
| `poll` | 挙手 / 先に当ててから明かす——**正解が 1 つだけあるとき**に限る。ここが `quiz` や `discuss` との境界線である | 2 段構成 |
| `discuss` | オープンな議論 / 意見の集約：問い + どんな答えを期待するか + それをどう使うか。**模範解答は無く、話者は集めるだけ** | 議論カード、反応は `hint` に落ちる |
| `handoff` | 次の話者への引き継ぎ | 分担執筆のデッキ |

> 審査の想定問答はもう独立したキーワードを持たない：問いはそのスライドの `counter` に、答えはその `hint` に書く。かつての `qa` は `hint` とほぼ一語一句重複していたので削除した。

### 場面別のスターターセット（出発点の一枚——それでも実際に使う分だけに削る）

| 場面 | 内核の 3 語以外のキーワード（`sec` は内核なので重複して挙げない） |
|---|---|
| 授業 | `topic title sub defs example steps points visual layout emphasis quiz takeaway hint` |
| データ報告 | `topic title kpi table compare bars data visual emphasis caveat takeaway action hint` |
| 審査 / レビュー | `topic title points data table compare evidence caveat takeaway action counter hint` |
| 技術トーク | `topic title sub code diagram steps before-after demo example takeaway hint` |
| ピッチ / 説得 | `topic title kpi quote pull points compare timeline media emphasis ask lines hint` |

**語り手がいなければ → `lines` / `role` / `handoff` は選ばない。** 単一声のデッキにセリフを無理に押し込むと、上の 1 つの様式がまた唯一の様式に戻ってしまうだけである。

### 選定ルール

1. 内核の 3 語は必須；残りはページ型で選び、1 スライド合計 5–11 語。
2. キーワードの順序 = スライドの上から下への順序；構築はその順で DOM を組む。
3. 1 つの考えに 1 つのキーワード：`points` **または** `prose`、両方は使わない；`table` を使ったなら同じ数字を `data` に書き写さない；`takeaway` は `key` を復唱してはならない。
4. 使わないキーワードの行はまるごと落とす——空欄も「なし」も書かない。
5. `type` がそのページの既定のキーワードの組み合わせを決める——**同じ `type` のスライドは残りのキーワードも同じにする**。8 つの名前がキーワードとページ型の両方を兼ねる（`toc` `steps` `quiz` `task` `demo` `before-after` `caveat` `timeline`）：`- type:` のスロットにあればページ型、`- name:` のスロットにあればキーワードの内容であり、1 つのスライドに両方が現れるのは普通のこと（`- type: steps` と `- steps: 1./2./3.`）。ルール 5 が統べるのは後者のほうである。
6. **`points` は受け皿ではない。** 欠けているものは `missing` へ、2 つの見分け方は `compare` へ、4 行を超える一覧や状態の列が要るものは `table` へ、聴衆の声は `discuss` へ——「これに当てる語があるか」を先に問い、「箇条書きにできるか」は後で問う。何でも `points` に放り込むなら、拡張したライブラリも 8 フィールドのままということになる。

### ページ型ライブラリ（`type` の値、場面別のグループ）

- **構造系**：cover / toc / agenda / act-divider / two-column / cast / verdict / closing / references / thanks / team
- **データ系**：data-contrast / data-cards / kpi-hero / table-showdown / chart-line / chart-bars / chart-stack / rank-list / breakdown
- **論証系**：split-compare / evidence-grid / case / counter-argument / caveat / framework / root-cause / next-steps / timeline / policy-timeline / lifecycle-strip / before-after
- **教材系**：concept / definition / example-worked / steps / diagram-explain / quiz / task / discuss / recap
- **技術系**：arch-diagram / code-walkthrough / terminal-log / demo / pitfall / changelog / roadmap
- **研究とピッチ**：related-work / method / experiment / results / ablation / limitation / contribution / problem / solution / market / traction / business-model / competition / the-ask

スライドが既存のどの型にも本当に当てはまらない → 新しく作ってよい。ただし §3 とキーワード宣言にも必ず入れ、1 つのデッキで新造できる型は最大 2 つ。

**ステップ 2 のテンプレート一覧と名前が食い違うとき**：レイアウトテンプレート J–Q はそれぞれ「相性のよいページ型」のヒントを別の語彙で載せている（`stat-highlight` ≈ `kpi-hero`、`section-divider` ≈ `act-divider`、`big-quote` ≈ `pull` を載せるスライド、`pros-cons` ≈ `split-compare`、`process-steps` ≈ `steps`）。それらの名前は、そのテンプレートが何をうまく並べられるかを述べているだけである。**§4 のこの語彙が本デッキ唯一のものである**：テンプレートを選んだら、使う `type` 名をキーワード宣言に 1 通りだけ書き、類語を混ぜない（`kpi-hero` と `stat-highlight` が同じ文書に出てくるのは 2 つの真実である）。名前を変えたことは §6 に 1 行記録する。

### スライドの書き方

最初の例は行末にコメント（`<!-- -->`）を添えてあり、この語彙に初めて出会う人が照らし合わせて読めるようにしている。書くかどうかは任意——レビュー用の凡例がすでに語集合を一度説明しているので、後の 2 例は実際の骨子が使う簡潔な形で示す。**コメントが HTML になることは決してない。**

```markdown
### s6 · 第 3 層：単価が安いことは総額が安いことではない（対比）
- type: split-compare            <!-- ページ型：同じ口径、2 つの側 -->
- topic: ライフサイクルコスト     <!-- どのセクションか；眉標として描画される -->
- key: 単価が安いことは総額が安いことではない   <!-- このスライド唯一の主張 -->
- compare:                        <!-- このスライドの数字はすべてここに住む -->
  | 口径 | 何を数えるか | こちら側 | 比較対象 | source · year |
  |---|---|---|---|---|
  | ハードウェアのみ | 購入価格 | <単価の数字> | <数字> | <機関> · <年> |
  | ライフサイクル全体 | ハードウェア + 電力 + 運用 | <桁の差> | <数字> | 上の行から導出——**画面上では「これは <根拠> から我々が導出した」と表示する** |
- bars: 主となる棒が高さの異なる 3 つの積み上げ（低 / 混合 / 高）に分かれ、y 軸「¥/kWh·年」、x 軸に 3 つの口径を記す   <!-- どのグラフか -->
- emphasis: 反転後に最も高い積み上げが warn を取り、それ以外は panel   <!-- このスライド唯一の強い色はどこへ行くか -->
- ask: では「どちらが安いか」は、どの区間を数えるかにかかっている？   <!-- 投げかける問い -->
- lines:                         <!-- 語り手のセリフ；単一声のデッキではこの 2 行を削除する -->
  - A: <8–28 字、事実を 1 つ述べる>
  - B: <8–28 字、それを捉え直す>
- hint: ここで動くのは境界だけ、料金の話は開かない；口径を突っ込まれたら付録の s18 へ飛ぶ   <!-- 話者にだけ見える -->

```

```markdown

- type: concept
- topic: 3 つのキーワード
- key: 無料になったのは複製であって、生産ではない
- title: 限界費用がゼロに近づくこと
- defs:

  - 複製費用 = 同じものをまた 1 人に渡すといくらかかるか

  - 「安くなった」と言うとき、それは後者のほう
  - 前者は安くなっていない
  - 混同すると結論が誤る
```

```markdown
### s14 · なぜ 1 クリックでページが飛ぶのか（コード · 語り手なし）
- type: code-walkthrough
- topic: 3 つの既知の罠
- key: 独自のクリック可能要素はクリック判定から除外しなければならない
- title: stopPropagation の 1 行
- code: `deck-shell.js` のクリック判定、JS、44 行目と 46 行目だけを読む

  1. シェルは画面の左右半分をページ送りとして扱う
  2. 用語チップの click が body までバブリングする
  3. だから用語をクリックするとページがめくれる
- before-after: 改修前——用語をクリックすると先へ飛ぶ / 改修後——その場に留まり、空白部分だけがページをめくる
- takeaway: オーバーレイ内のクリックできるものはすべてイベントを飲み込まなければならない
- hint: コードはライブで走らせず、3 秒のキャプチャを再生する；「なぜ pointer-events を使わないのか」と聞かれたら「それでは文字の選択も一緒に死ぬ」と答える
```

1 つの宣言済み語集合から 3 枚のスライドを作り、まったく違うキーワードで埋めている：データのスライドは `compare` / `bars`、概念のスライドは `defs` / `example` / `quiz`、コードのスライドは `code` / `steps` / `before-after`。だからこそ語集合はデッキごとに宣言する。

上のすべての `<…>` はプレースホルダである：資料ファイルから値を埋め、骨子に括弧を残したり、でっち上げた数字を置いたりしてはならない。

### スライドごとのハード制約

- **エビデンスルールはフィールド名ではなく数字に従う。** どのキーワードであれ数字が現れたら——`table` `kpi` `compare` `rank` `timeline` `formula`、`code` の中のベンチマーク出力、そして `example` `quote` `counter` `analogy` がついでに引用する数字——値 / 単位 / 年 / 出典の 4 つがそろい、資料ファイルの 1 行に対応づけられなければならない；導出値は「…から導出」と書き、係争中は ⚠️ を付け、孫引きは「…経由」と書いて 🔍 を付ける。数字が 2 つ以上のキーワードにまたがるときは、監査のためにそれらを索引する `data` の行を足す——「どのキーワードのどの行 → 出典」であり、値を打ち直すことではない；1 か所に収まっているときは足さない。
- 1 スライドの数字は最大 4 個；残りは `hint` に入れる。本当にもっと必要なら → スライドを分割するか、同じ口径の数字を 1 つの `table` 行にまとめる。
- 文章より比較を優先する；`visual` / `layout` / `diagram` は、どのグラフか、軸のラベル、列の幅、どのブロックが warn を取るかを名指ししなければならない——「グラフを足す」「きれいにする」は指示ではない。
- 1 スライドに強い色は 1 つ、どれかを `emphasis` が示す。
- `sec` の合計はステップ 1 の時間予算に近づけなければならない；超過したらまずキーワードを削り、次にスライドを削る。

## §5 実装メモ

構築ステップが実行する番号付きの一覧：DOM の骨格とクラス名、**キーワード → DOM スロットの対応表**（宣言した各キーワードがどの要素に描画されるか——構築が推測しなくて済むよう §4 ライブラリの「どこに落ちるか」列から写す；新造したキーワードにはここで独自のスロットを書く）、データ提示の優先順位、語り手カプセルの可視性ルール（`lines` / `handoff` が語集合に入ったときだけ）、⚠️/🔍 バッジの使い方とその説明をどこでするか（出典ページ）、禁止事項（出典の無い数字、エビデンスの代わりの形容詞、発見として述べられた推定、訂正済みの誤読の繰り返し）、拡大縮小と印刷、そして**出力とセルフチェック**（スライドごとに：すべての数字が資料ファイルに見つかる；ナビゲーションとキーボードが動く；外部リクエストが無い；既知の難所のスライドが正しく書かれている）。

## §6 変更履歴

日付を添えて `変更 | 説明` の行を追記する。ユーザーの場当たり的な編集（スライドの追加、タイトルの変更、グラフの作り直し）も記録し、「現状が優先」と注記する。骨子と HTML が食い違ったら、常に骨子を直す。

## §7 スピーカープロンプト（任意 · 最後のセクション、レビューのために作る）

**ステップ 8（発表者モード）が有効なときにだけ書く。** これは発表者ウィンドウのプロンプトカードに表示される文言である。agent が §4 の各スライドの `key` / 数字を担うキーワード / `hint` / `ask` / `lines` から生成し、**骨子文書のいちばん最後**に置く；ユーザーが編集し承認してはじめて、ステップ 5 がそれをそのまま各スライドの `<aside class="notes">` に移す（`display:none` で聴衆から隠し、スライドには決して印刷しない）。

ルールは 3 つ——どれか 1 つでも破ったら書き直す：

1. **台本ではなく信号である。** 核となる語を太字にし（`<strong>`）、転換を `<em>` で示し、各遷移に独自の短い段落（1–3 文）を与える。そのまま読み上げられる版は役に立たない——舞台で誰も逐字で読んだりしない。
2. **1 スライド 150–300 字。** それ未満だと文の途中で止まり、それ以上だと時間内に走り読みできない。ステップ 1 の時間予算と突き合わせる：1 スライド 2–3 分が心地よい速度である。
3. **書くのではなく話す。**「したがって」→「だから」、「前述の解決策」→「このやり方」、「最適化される予定」→「調整した」。一度声に出して読む。話し言葉に聞こえるなら合格である。

数字は資料ファイルの契約の下にとどまる：プロンプトに現れるすべての数値は、そのスライドでそれを担う §4 のキーワード（`data` / `table` / `kpi` / `compare` / `formula` …）に対応する出典を持たなければならず、導出 / ⚠️ / 🔍 の言い回しもそこでは声に出して言わなければならない（「これは X から計算した——境界は議論の余地がある」）。**§7 は新しい事実を足す場所ではない。**

```markdown
### s6 プロンプト（§4 s6 に対応 · sec 60s）
- 開口：では<strong>単価</strong>だけで見れば我々は 2.1 倍安い——そしてそれこそが、今日解体しようとしている主張である。
- 転換：<em>境界をライフサイクル全体へ移す</em>：左の棒はハードウェアだけを数えている。電力と運用を入れた瞬間、順序がひっくり返る。
- 投げかけ：つまり「どちらが安いか」は、どの区間を数えるかで決まる。
- 引き継ぎ（s7 へ）：ではその境界はどう引くのか。次のスライドがルールを示す。
```

この 4 つのフィールドが形式である：**開口 / 転換 / 投げかけ / 引き継ぎ**、それぞれ 1–2 の短い段落、合計 150–300 字。構築時にそのスライドの `.notes` の中の `<p>` 段落になり、カード内では `<strong>` が warn 色、`<em>` が accent 色で描画される（`08-presenter-mode.md` 参照）。

§7 の後ろには何も続かない。ステップ 8 を使わないなら、このセクションごと省略し、§6 に「発表者モードは有効化していない」と 1 行書く。

## レビューゲート（このステップの終わり）

骨子のパスを、3–5 行の案内とともにユーザーへ送る：スライド数と合計時間、各幕が何をするか、どのスライドがフックか係争スライドか、どの数値が導出か ⚠️/🔍 付きか、そして判断を仰ぐ 2–3 点（例：「ニュースのつかみのスライドは残すか」「語り手は 2 人か 3 人か」）。案内にもう 1 つ書く：**§4 の冒頭にある「レビュー用の凡例」ブロックがユーザーの用語集である——スライドを 1 枚ずつ読む前にそこを流し読みし、説明できていない語があればそれはそのブロックの穴である**。**§7 があるなら、案内で別途こう指摘する：スピーカープロンプトは骨子の X 行目から始まる——それぞれが自分なら実際に言いそうな言葉かを確認してほしい**。プロンプトの言い回しを直せるのは登壇する本人だけだからである。

**ステップ 5 の前に、承認か修正を待つ。** ユーザーの修正は骨子ファイルに反映する——チャットの中だけに書かない——そして数値が変わったときは資料ファイルも更新する。
