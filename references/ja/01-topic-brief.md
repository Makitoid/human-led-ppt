# ステップ 1 · テーマと構成

目標：手を動かす前に「誰が見るのか、何を話すのか、どれくらいの長さか、どう組み立てるか」を確定させる。このステップは議論だけ——ファイルは書かない（結論はユーザーに貼って確認を取り、あとで骨子 §0 に写す）。

## 必ず聞き出す 5 つ

一度にまとめて聞く。質問を小出しにしない。ユーザーが答えられない項目には具体的な既定案を出し、「どこを変えるか」だけで返せるようにする。

1. **テーマと中心の問い**：このプレゼンが何に答えるのかを 1 文で。中心の問いは、そのまま 1 枚のスライドに載せられる疑問文でなければならない（例：「AI は知能を安くした。では何を高くしたのか」）。中心の問いが無いデッキは資料の山になる。
2. **聴衆と場**：授業の発表 / 論文審査 / ピッチ / 社内共有 / 一般向け講演。これで情報密度、専門用語をどこまで説明するか、署名や分担のページが要るかが決まる。
3. **所要時間とページ数**：分 → 枚数。目安は語りのスライドが 40〜60 秒、データの濃いスライドが 60〜80 秒。10 分 ≒ 12〜16 枚、20 分 ≒ 22〜28 枚。**決めた枚数は骨子 §1 に書き、構築中に超えない。**
4. **構成と幕**：次節から 1 つ選び、幕ごとにページ範囲と所要時間を割り当てる。あわせてフック / ビルド / ピーク / リリースの 4 つの拍点が、それぞれどのページに落ちるかを決める。
5. **素材と署名**：既存の資料 / データ / 上からの要求はあるか。署名、分担、付録、出典ページは要るか。必ず入れる内容、必ず避ける内容はあるか。

## 語りの構造の選び方

| 構造 | 向く場面 | 幕の骨格 |
|---|---|---|
| 問題提起 → 分析 → 結論 | 授業の発表、論を積む説得（既定の推奨） | 数字や対比でつかむ導入 → 問いを重ねる → 立場が収束 + 開いた問いを 1 つ |
| 結論先出し → 三点の支え → 行動 | ピッチ、審査、意思決定者 | 結論のスライド 1 枚 → 根拠 ×3 → リスクと次の一手 |
| 時系列 / 変遷 | 歴史、技術動向、プロジェクトの振り返り | 出発点 → 転換点 → 現在 → 分岐 |
| 対比の並置 | 案の選定、競合、A vs B | 双方の輪郭 → 同じ物差しでの比較 → どちらをいつ選ぶか |
| 事例の連続 | 経験の共有、授業 | 事例 → 引き出した法則 → あなたならどうするか |

問い詰め型（インタビュー型）の構造では、エンジンは問いの連鎖であり、各ページがそれを少なくとも 1 リンク進める：
`数字はいくつか → 数字はどこから来たか → その数字は誰が出したか → 境界を変えても成り立つか → では誰がコストを払うのか → 解はあるか → そのトレードは割に合うか`

立場ごとに語り手を分ける必要があるときは、2〜3 個のコードネーム（例：ENG / LCA / POL）を使う。ルールのページに登場させ、以降は各ページ下部のカプセルとして常駐させる。**語り手の数は 1 ページあたりの情報量をそのまま増やす——少ないほどよい。**

## 語りの弧（構造とは別に必ず決める）

構造が答えるのは「何幕に分けるか」だけであり、弧が答えるのは「聴衆がどのページでつかまれ、どのページで説得されるか」である。どの稿にも 4 つの拍点が要り、要件確認ブロックに書き込む：

| 拍点 | 役割 | 落ちる場所 |
|---|---|---|
| フック hook | 期待を裏切る：対比、代償、直感に反する数字 | 前半 20%、遅くとも 3 枚目 |
| ビルド build | 問いを重ねるか証拠を積み増す。各ページが少なくとも 1 段進む；途中に低い所を置いて息継ぎしてよい | 中盤 |
| ピーク peak | デッキ全体で最も強い結論 / 最大の代償 / 最大の反転 | 後半、**デッキ全体で 1 つだけ** |
| リリース release | 聴衆が持ち帰れる 1 文に戻し、境界か次の一手を示す | 最後の 2–3 ページ |

- **平らに並べない。** 同じ機能が 3 ページ続く（ずっと背景、ずっと数字、ずっと結論）のは資料の山である：統合するか、順序を入れ替えるか、削る。
- **各幕は中心の問いへの答えを変えなければならない。** その幕が終わったとき答えが A から B へ変わる；あるいは「まだ答えていない、どこで止まっているか」を明示する。答えが変わらない幕は隣の幕に統合する。
- **ピークは証拠で立ち、声量では立たない。** ピークのページは最も硬い証拠か最大の代償で支える。より大きな文字サイズ、より明るい色、より多いモーションでは支えない。
- **短い稿にも弧は要る。** ≤ 8 ページなら独立したビルドのページは省いてよいが、フックとリリースは省けない；4 拍すべてが平らな短い稿も組み直す。
- **時間はテンションに従う。** ピークのページは `sec` を十分に取り、つなぎのページは 30 秒以内に圧縮する；時間を全ページに均等に割らない。

## 要件確認ブロック（ユーザーに貼る）

```
テーマ：<一文で>
中心の問い：<スライドに載る疑問文>
聴衆／場：<…>  所要時間：<N> 分 → ページ数：<M> 枚（表紙と出典ページを含む）
構成：<三幕 / 結論先出し / …>
  第 1 幕 s1–sX（役割、時間）
  第 2 幕 …
  第 3 幕 …
弧：フック sX（<一文>）→ ビルド sX–sY → ピーク sZ（<一文>）→ リリース sX–sY
語りの仕掛け：<問いの連鎖 / 対比 / 時系列>、語り手：<なし | コードネームの一覧>
必ず入れる：<署名、分担、指定データ、指定事例>
必ず避ける：<…>  素材：ユーザー提供済み | ウェブ調査が必要 | 混在
出力先：<パス>  ファイル名：<トピック>.html
```

ユーザーの確認を得てからステップ 2（スタイル）へ進む。ユーザーが明確に「任せる」と言った場合は、上のブロックを埋めて貼り出し、委任された決定の記録として残してから続ける。
